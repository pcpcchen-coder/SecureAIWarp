# 11 實地試驗：Agent 能不能替沒見過的應用裝殼

日期：2026-11-26　｜　核心版本：第一輪 `6efea8d`，第二輪 `ff7f0e0`　｜　原始資料：[`trials/`](../trials/)

## 1. 結論

**前提部分成立，尚未達到第 1 期的完成標準。**

- 殼本身守得住：16 次裝殼（8 個應用 × 2 輪）產生的宣告都很緊，探針全數被擋，沒有任何一次靠放寬權限過關。
- 流程在修正後順利很多：第二輪 8 個應用中有 5 個一輪試穿就裝好、測試在強制模式下全過。
- 但「無人介入完成」仍只有 2/8，離 70% 的標準很遠。剩下的不是 bug，而是六個需要決定方向的設計缺口（第 5 節）。
- 最重要的一項修正是對設計假設的：**應用既有的測試幾乎不產生權限證據**。原則三「測試就是規格」需要改寫（第 4.1 節）。

| --- | :-: | :-: |
| 無人介入走完流程 | 1/8 | 2/8 |
| 技術上裝好（強制模式測試全過＋探針全擋＋功能可用） | 3/8 | 5/8 |

## 2. 方法

### 2.1 三種角色互相隔離

| 角色 | 數量 | 拿到什麼 | 不知道什麼 |
| --- | --- | --- | --- |
| 開發者 Agent | 每個應用 1 個 | 一句使用者口吻的需求、一個儲存庫外的空目錄 | Warp、沙箱、應用之後會被隔離 |
| 安裝 Agent | 每個應用每輪 1 個（全新） | 技能檔、`warp` 執行檔、應用目錄、這台機器的網路說明、步驟 0 三題的答案 | 核心原始碼、設計文件、其他應用、上一輪的結果 |
| 主持人 | 1 | 一切 | — |

主持人不採信安裝 Agent 的自述。每個結果都獨立重做：比對應用檔案雜湊（確認沒被偷改）、重跑 `warp lint`、在強制模式下重跑測試、重跑 `warp probe`、檢查 `exceptions` 有沒有被自行簽核、閱讀宣告內容。

步驟 0 的三題答案固定為：給特定對象用／對方在自己機器上執行／使用者自備金鑰。安裝 Agent 被告知「人不在線上，遇到要人決定的地方不要替人決定」。

### 2.3 模擬上游

這台機器的閘門連不到真實網路，所以在獨立的網路命名空間架了一個模擬伺服器，以真實主機名稱提供 Open-Meteo、ExchangeRate-API、Anthropic Messages API 與幾個一般網站。應用不需要改任何設定，TLS 驗證照常通過。每個請求都有紀錄，用來確認流量真的到達、以及金鑰是真值還是誘餌。程式在 [`trials/_harness/mocknet/`](../trials/_harness/mocknet/)。

### 2.4 兩輪之間改了什麼

第一輪結束後才修改核心與技能檔，然後用乾淨的應用副本與全新的安裝 Agent 跑第二輪。

- **核心**（`9822a80`…`0394985`）：殼內本機迴路不再被送進閘門；Node.js 只在需要時啟用代理；CONNECT 隧道裡的明文 HTTP；啟動指令與參數中展開 `${USER_PICK:x}` 等佔位字；不合格式的資料夾名稱直接報錯；標籤改為陳述「最後一次強制執行的指令與結束碼」；初稿產生器的五個錯誤。
- **技能檔**（`ff7f0e0`）：從 143 行改寫為 414 行，內嵌宣告欄位參考與殼內環境說明，新增「已知限制」一節教 Agent 辨認走不通的情況並停下。
- **不相干但同時發生**：第二輪的核心也包含 [10](10-security-review.md) 的安全強化（PR #1）。這是一個沒有控制的變因，但那批修改不影響裝殼流程。

探針在全部 16 次都是 100% 被擋（72–79 項，視宣告內容而定）。

### 3.2 守住了什麼

- **16 次裝殼沒有任何應用檔案被修改**。需要改應用時，安裝 Agent 都依規定產生修補檔、在副本上驗證、交給人決定（4 次）。
- **16 次都沒有自行簽核例外**，即使格式上只要填三個欄位就能通過檢查器。
- **試穿過程中權限增加的次數是 0**。初稿到定稿只有收緊：三次把不必要的寫入判定為維持阻擋（字型快取兩次、Go 工具鏈遙測一次），並以測試結果與逐像素比對確認不影響功能。
- **宣告都很緊**：沒有萬用字元、沒有 `app-visible` 機密、對內連線都只開本機迴路。

### 3.3 殼在真實漏洞上的作用

md-site 第二輪的安裝 Agent 在盤點時發現：應用使用的套件會把筆記開頭特定格式的區塊當成 JavaScript 執行。拿別人給的筆記來轉檔，等於執行別人的程式碼。開發者 Agent 與應用的測試都沒有發現。

套上殼之後，這段程式碼連不了網、讀不到筆記資料夾以外的檔案、只能寫進使用者選定的輸出資料夾。這是「殼限制損害範圍，不保證程式正確」第一次在非刻意植入的漏洞上得到印證。

## 4. 發現

### 4.1 對設計假設的修正：測試幾乎不產生權限證據

原則三寫的是「在側錄模式下跑測試得到它實際需要什麼」。實際上：

| | 來自應用的測試 | 來自安裝 Agent 手動操作 |
| --- | :-: | :-: |
| 對外連線的證據（4 個連網應用） | 0 | 全部 |
| 使用者資料夾的證據（5 個應用） | 0 | 全部 |
| 應用資料目錄的證據（4 個應用） | 0 | 全部 |

原因很一致：寫得好的測試會把網路擋掉或換成假伺服器、用暫存目錄而不是真實資料夾。測試越規矩，越不會碰到需要授權的通道。

測試仍然有用，但用途不同：它證明的是「**加了殼功能沒壞**」，而不是「功能需要哪些權限」。權限證據實際上來自安裝 Agent 依 README 操作應用。建議把原則三改寫成這兩件事分開陳述，並把「由 Agent 依功能清單實際操作」從補充手段升為主要手段。

### 4.2 設計層級的缺口（未修，需要決定）

依對「交給別人用」的影響排序。

**D1　沒有同意流程，而最常見的需求剛好需要它**（3/8）
「可修改使用者選定的資料夾」是軟性規則，需要人核可並寫入 `exceptions`。但核可的指令不存在，三個檔案處理工具都只能停在這裡。而且 `exceptions` 只是三個文字欄位，Agent 自己填也能通過檢查器——這次沒人這麼做，靠的是守規矩而不是機制。
建議：(a) 實作由終端機直接詢問人的 `warp approve`，簽核紀錄由核心寫入；(b) 重新考慮這條規則本身——資料夾是接收者在啟動時自己選的，同意已經隱含在選擇裡，把它當成標籤上明顯標示的一般授權可能更合理。

**D2　相依環境帶不走**（Python 與 Node.js 應用全部受影響）
虛擬環境裡的指令入口寫死作者機器的絕對路徑；應用內容雜湊涵蓋了 `.venv` 與 `node_modules`，接收者重建相依環境後雜湊必變、所有證據失效；`node`、`npm`、`go` 這類裝在固定系統目錄以外的工具在殼內看不到（試驗靠一個繞道才讓 Node.js 應用跑得起來）。
這表示目前的交付方式其實只對「沒有相依套件的腳本」成立。建議：宣告中加入工具鏈與相依來源的聲明，接收者端由核心在殼內依鎖定檔安裝相依（建置期也在殼內，只能連套件庫），雜湊只涵蓋原始碼與鎖定檔。

**D3　用誘餌金鑰側錄，看不到 API 成功之後的行為**（2/8）
weekly-digest 要等模型回應成功才寫出週報，但側錄用的假金鑰讓 API 回 401，寫檔永遠不發生，也就永遠拿不到授權。安裝 Agent 只能把輸出改到螢幕，並使用一筆失敗的側錄當作對外連線的證據。
建議：側錄時允許由閘門注入真金鑰（應用仍然看不到真值，金鑰也只送往事先指定的主機），搭配合成資料。

**D4　呼叫語言模型的應用在沒有花費上限的情況下通過**（1/8）
安裝 Agent 把模型 API 當成一般對外主機宣告，檢查器零警告，標籤完全沒提會花模型費用。「有 AI 呼叫必須有花費上限」這條硬性規則只在宣告了 `ai` 區段時才生效，不寫就繞過了。第二輪的安裝 Agent 是刻意不寫的，理由是預算該由人決定——判斷合理，但結果一樣。
建議：檢查器內建常見模型 API 主機清單，對外連線命中卻沒有 `ai` 區段時報錯；AI 閘門實作前，標籤要明寫「會使用你的金鑰呼叫模型，花費未受限」。

**D5　金鑰不在標頭就無法授權**（1/8）
expenses 把金鑰放在網址路徑。機密代理只能注入標頭，所以金鑰無從提供，外幣換算在殼內靜靜失效，而測試、探針、標籤全部顯示正常。
建議：閘門本來就會中止綁定主機的 TLS，可以支援在網址路徑與查詢字串中替換佔位值。

**D6　對外主機取決於使用者資料時無法表達**（1/8）
linkcheck 要連哪些網站取決於使用者文件的內容。宣告只能列具體主機，結果是裝好了但對接收者沒用，而且被擋下的網址會被工具報成「壞連結」。爬蟲、RSS 閱讀器都屬於這一類。
建議：新增一種對外類別「任意公開網站」，限 GET／HEAD、封鎖內部網路、設流量上限，列為需核可的例外並在標籤上以最醒目的方式標示。

**D7　應用目錄唯讀，與「把資料寫在程式旁邊」的習慣衝突**（4/8）
kanban 的測試把暫存檔寫死在應用目錄，沒有設定可改，23 個測試只能過 3 個；expenses、kanban 的資料庫預設也在應用目錄。有文件記載的環境變數時可以繞過，但宣告沒有設定環境變數的欄位，只能寫在啟動指令裡。更麻煩的是，這類失敗完全不會出現在帳本或阻擋訊息裡。
建議：側錄與跑測試時給應用目錄一層用完即棄的可寫覆蓋層；宣告加入 `env` 欄位；讓檔案寫入被擋這件事看得見。

**D8　信任等級的判定依據不成立**
L2 取決於最後一次強制執行的結束碼。第一輪觀察到五種失真：測試失敗後再跑一個會成功的指令就升回 L2；找到壞連結回傳 1 的正常結果被當成失敗；伺服器以 Ctrl+C 結束被當成失敗；18/23 的測試結果不出現在標籤上；核心功能失效但結束碼為 0 所以顯示正常。第二輪已把措辭改為陳述事實，但判定條件沒變。
建議：宣告中明確指定測試指令，L2 綁定到「該指令在強制模式下對這份宣告與這份內容的執行結果」；並承認結束碼只是必要條件。

## 6. 建議的優先順序

1. **D2 相依環境**與 **D1 同意流程**：這兩項不解決，「交給別人用」對大多數應用不成立。
2. **D4 模型花費**：改動小，卻是目前唯一一個「硬性規則實際上繞得過」的地方。
3. **D7 可寫覆蓋層與 `env` 欄位**、**D5 網址中的金鑰**、**D3 側錄時注入真金鑰**：各自解鎖一類常見應用。
4. **D8 信任等級**：需要先決定「什麼算功能驗證」。
5. **D6 任意公開網站**：影響的應用類型較少，且需要仔細設計才不會變成後門。
6. 改寫原則三（4.1），並修掉 4.3 的核心 bug（`diff`、探針用語、標籤顯示 `denied_by_design`）。

D1、D2、D4 完成後值得重做一次同樣的試驗。

## 7. 這次試驗的限制

- **樣本小且同源**：8 個應用，全部由同一個模型家族產生，需求由主持人擬定。真實世界的應用會更亂。
- **只測了一種 Agent**：開發者與安裝 Agent 用的是同一個模型。「在兩種以上編碼 Agent 上驗證技能檔」仍未做。
- **沒有真人看標籤**：人的步驟是模擬的。標籤是否真的讓不懂技術的人看得懂、會不會造成同意疲勞，完全沒有驗證。
- **模擬上游**：外部 API 的行為是照文件與少量實測樣本仿製的。expenses 的修補檔假設真實 API 接受標頭形式的金鑰，只在模擬伺服器上驗證過。
- **試驗繞道**：為了讓 Node.js 應用在殼內找得到 `node`，機器上放了一個包裝程式；第一輪它還會自動開啟代理設定，造成 md-site 一個測試失敗（已在結果中標明）。沒有這個繞道時，3 個 Node.js 應用在第一步就會全部失敗——這屬於 D2，沒有計入成功。
- **角色隔離有四處瑕疵**：第一輪兩個安裝 Agent 讀了環境設定檔（看到測試金鑰的值）、一個對 `warp` 執行檔跑了 `strings`；第一輪八個 Agent 共用暫存區，發生一次目錄誤用與一次可能的程序誤殺（受影響的都是拋棄式資料）；第二輪兩個 Agent 依技能檔移動無用側錄檔時被執行環境的權限檢查擋下。都不影響宣告內容。
- **只測了 root 身分、情境 A 與 C、Linux**。
- **兩輪之間核心有不相干的變動**（安全強化）。
