# 10 核心安全審查紀錄（2026-11-25）

對第 1 期核心（`internal/sandbox`、`internal/gate`、`internal/netpolicy`、`internal/runner`）做的一輪對抗式審查。
方法：讀完上述套件的全部程式碼，列出疑點，再把每個疑點放進真的殼裡實測；只有重現得出來的才列為漏洞。
審查者是 AI，不能取代 [09](09-roadmap.md) Q5 要求的獨立人工審查。

## 1. 已重現並修補

| # | 嚴重度 | 問題 | 影響 | 修補 |
| --- | --- | --- | --- | --- |
| 1 | 嚴重（僅 root 執行時） | 殼內可寫主機的 `/proc/sys` | `/proc/sys` 的權限檢查看的是使用者 ID 而不是 capability。warp 以 root 執行時，殼內 UID 0 就是主機的 root，應用可改寫 `kernel.core_pattern`（下一次有程序當掉時，主機會以真正的 root 執行指定程式）、觸發 sysrq 等：完整逃出殼 | `/proc/sys`、`sysrq-trigger`、`irq`、`bus`、`fs` 改為唯讀掛載；`kcore`、`keys`、`kallsyms` 等遮蔽。無法設定 `max_user_namespaces=0` 時改為拒絕啟動 |
| 2 | 高（root 與一般使用者皆然） | 殼內繼承主機的 session keyring | session keyring 會跨 `clone()` 繼承，進入新的使用者命名空間後仍算「持有」。應用可用 `request_key`／`keyctl` 讀出啟動 warp 的那個登入階段 keyring 裡的金鑰（Kerberos 票證、fscrypt／eCryptfs／CIFS 憑證等） | 啟動應用前加入一個新的、空的匿名 session keyring |
| 3 | 中 | 核心的控制 socket 漏進殼內（fd 3） | 應用可對核心偽造控制訊息；送出第二個 `started` 就讓核心 panic，跳過結束時的收尾（上傳用量不落盤、沒有結束紀錄與強制報告）。呼叫 warp 的程式若漏了其他描述元，也會一路傳進殼內 | 殼的 init 一開始就把 stderr 以上的所有描述元設為 close-on-exec；核心對重複的 `started` 不再 panic |
| 4 | 中 | 請求標頭沒有大小上限 | 對外閘門的記憶體不在殼的記憶體上限內。應用送一行沒有結尾的標頭，核心就一直緩衝，可耗盡主機記憶體 | 每個請求的請求列＋標頭上限 1 MiB，超過即中斷（明文與中止 TLS 的通道都套用） |
| 5 | 中 | 每日上傳上限只算請求內容 | 經檢視的通道（明文 HTTP、中止 TLS）只計 body；把資料放在網址與標頭、不帶 body，就不受 `upload_per_day` 限制。另外用量只在正常結束時落盤 | 請求列與標頭計入用量；用量至少每秒落盤一次 |
| 6 | 中 | 對內閘門的權杖 cookie 跨連接埠外洩、同站跨來源請求 | 瀏覽器的 cookie 不分連接埠：另一個殼的權杖 cookie 會被轉送給這個殼裡的應用；本機另一個連接埠上的網頁（例如另一個殼裡的惡意應用）也能帶著 cookie 對這個應用發出請求（`SameSite` 把所有本機連接埠視為同站） | 轉送前移除所有 `warp_token_*` cookie；`Origin` 標頭存在且不是閘門自己的來源時拒絕 |
| 7 | 低 | TLS 交握不帶伺服器名稱可通過 SNI 檢查 | 對未中止 TLS 的主機，不帶 SNI 的 ClientHello 不會被比對，可在共用前端上繞過「SNI 必須等於核准主機」 | 目的地是主機名稱而 ClientHello 沒有 SNI 時拒絕（IP 目的地不受影響） |
| 8 | 低 | 機密可被以明文送往 TLS 連接埠 | 應用決定用 `http://` 還是 `https://`；對綁定主機的 443 埠發明文 HTTP，真值就以明文出現在網路上 | 帶有機密佔位值的明文請求送往 443 埠時拒絕 |
| 9 | 低 | Azure WireServer `168.63.129.16` 被當成公開位址 | 它在公開位址範圍內，但只有 VM 自己連得到，提供擴充功能設定等敏感資料；側錄模式或宣告的主機解析到它時可連上 | 列入中繼資料位址 |

## 2. 看過、目前沒有發現問題

- 應用以新的 session 啟動、沒有控制終端機，所以拿不到 `TIOCSTI`（往使用者終端機塞按鍵）；這一點靠的是 `Setsid`，不要拿掉。
- 殼的 init 不可傾印，應用讀不到 `/proc/1/environ`、`/proc/1/root`，也無法 ptrace。
- 應用沒有任何 capability，且 bounding set 為空、`no_new_privs`：無法卸載或重新掛載任何東西，無法建立巢狀使用者命名空間。
- 使用者 keyring（`@u`）與 persistent keyring 依使用者命名空間分開，殼內看到的是空的。
- 抽象 unix socket 依網路命名空間分開；路徑型 unix socket 只有在被掛進殼的目錄裡才連得到。
- 每次上游連線前都重新解析並檢查位址，撥的就是檢查過的那個 IP；IPv4 對映、NAT64、6to4、Teredo 都會被還原或拒絕。
- 上游的轉址不會被閘門自動跟隨；回應若使用無法檢視的內容編碼，在有機密時會被擋下。

## 3. 尚未處理（建議）

依重要性排列。這些沒有在本次修改。

1. **以 root 執行仍然較弱。** 殼內 UID 0 是主機的 root，上面第 1 項只是把已知的 `/proc` 控制介面擋掉（黑名單）。建議以 root 執行時預設拒絕、需明確加旗標才放行，或在 root 時把殼內 UID 對映到一個無權限的主機 UID。
2. **沒有 seccomp。** `keyctl`、`bpf`、`perf_event_open`、`io_uring` 等系統呼叫仍然開放；第 2 項之外的 keyring 操作、核心漏洞的攻擊面都靠它收斂。
3. **機密綁定沒有通訊協定與連接埠。** 宣告了綁定主機的 80 埠時，機密仍會以明文注入。建議 `secrets[].bind` 加上連接埠，並預設只在 TLS 上注入。
4. **執行中寫不進稽核帳本只會警告。** 啟動時寫不進會拒絕執行，但執行到一半（例如磁碟滿）之後的放行不再有紀錄。建議改為中止殼。
5. **機密遮蔽可用分段請求繞過。** 綁定主機若會回傳金鑰，應用可用 `Range` 把真值拆在兩個回應裡。與 [09](09-roadmap.md) 第 5 節「遮蔽只比對原文」同一類，根本解法是不要把會回傳金鑰的主機當作綁定主機。
6. **對外閘門的連線數沒有上限。** 每條連線在核心裡佔一個 goroutine 與緩衝區，數量只受殼內程序數與描述元上限間接限制。
7. **應用可改動終端機設定、輸出控制序列。** stdin／stdout 直接接到使用者的終端機。
