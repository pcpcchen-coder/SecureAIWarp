# 01 問題與設計原則

## 1. 問題的本質

傳統軟體的信任鏈是：**有人寫 → 有人審 → 有人負責**。AI 協作開發把中間那一環拿掉了：

- 程式碼由 Agent 產生，量大、變動快，人讀不完也不想讀。
- 驗證方式變成「跑測試、試功能」，也就是只驗證了**它該做的事有做**。
- 沒有人驗證**它不該做的事沒做**——而這正是把工具交給別人時，對方最在意的部分。

所以缺口很明確：**負向保證（negative assurance）**。功能測試證明不了「它不會把你的資料傳出去」。

再加上三個讓問題更難的現實：

1. **型態太多樣**：CLI、桌面程式、本機網頁、雲端服務、聊天機器人、MCP 伺服器、瀏覽器外掛、自主 Agent……不可能為每種型態各寫一套防護。
2. **作者沒有資安能力**：能做出應用的人，不一定知道什麼是 egress allowlist。
3. **安裝設定也是 AI 做的**：連「加上防護」這件事都要交給 Agent，而 Agent 本身會出錯、會被提示注入。

## 2. 核心觀察：型態無限，通道有限

不管應用長什麼樣子，它能對世界造成影響的途徑只有這幾條。殼只需要守住這些通道：

| # | 通道 | 它回答的問題 | 典型事故 |
| --- | --- | --- | --- |
| 1 | **檔案** | 它能讀寫哪些路徑？ | 掃描家目錄、誤刪資料夾、讀取 SSH 金鑰 |
| 2 | **程序** | 它能執行什麼、能用多少資源？ | 執行下載來的指令、挖礦、fork 炸彈 |
| 3 | **對外連線** | 它能連到哪裡、送出什麼？ | 資料外洩、連到惡意套件的回傳主機 |
| 4 | **對內連線** | 誰能連到它？ | 服務綁在 0.0.0.0 無驗證、管理介面外露 |
| 5 | **機密** | 它能看到哪些金鑰？ | 金鑰寫死在程式、印到日誌、被相依套件偷走 |
| 6 | **AI 呼叫** | 它怎麼用模型與工具？花多少錢？ | 提示注入觸發危險工具、額度被刷爆 |
| 7 | **資料** | 哪些類別的資料會流向哪裡？ | 個資被送進第三方 API、留存過久 |
| 8 | **供應鏈** | 它是用什麼組成的？ | 幻覺套件名被搶註、相依套件有已知漏洞 |

前七條是**執行期通道**，由殼在執行時攔截；第八條是**建置期通道**，由殼在封籤前檢查。

「涵蓋大部分應用情境」的方法因此不是列舉應用型態，而是：**每種型態只是這八條通道的不同組合與不同攔截位置**（見 [06 應用情境](06-scenarios.md)）。

## 3. 七項設計原則

### 原則一：信任邊界，不信任程式碼
殼不嘗試理解或證明程式碼是好的。它假設程式碼可能有錯、可能含惡意相依，並把保護放在程式碼**之外**——作業系統、網路、代理層——這些地方應用程式自己改不了。

> 推論：靜態掃描只是輔助（用來提示風險、協助打版），不是保證的來源。

### 原則二：管通道，不管型態
所有政策都以通道表達，所有強制都發生在通道的閘門上。新型態的應用出現時，只需要新的「攔截接法」（adapter），不需要新的政策語言。

### 原則三：Agent 提案，核心執行
這是整個設計最重要的分工：

| | 安裝 Agent（Warp Fitter） | 核心（Warp Core） |
| --- | --- | --- |
| 性質 | 機率性、靈活、可能被騙 | 確定性、小、可稽核 |
| 負責 | 理解應用、產生宣告、解釋給人聽 | 驗證宣告、強制執行、留紀錄 |
| 產出 | `warp.yaml`（資料） | 攔截行為（機制） |
| 出錯的後果 | 功能不通，或標籤上多出一條顯眼的權限 | （必須盡量不出錯，因此要小） |

Agent **永遠不寫強制邏輯、不修改核心、不能關閉檢查**。它的自由度被限制在「填一份有固定格式的表」。

### 原則四：預設拒絕，憑證據授權
宣告檔裡的每一條權限都必須附上：
- **證據**：哪一次側錄、哪一個測試觀察到這個行為；
- **用途**：一句非技術人員看得懂的話。

沒有證據的權限，檢查器直接拒收。這讓 Agent「順手多給一點」變成不可能。

### 原則五：執法權在使用方
殼的強制執行跑在**實際執行應用的那一方**所控制的 Warp Core 上。作者交付的 Bundle 只包含宣告與證明，不包含執法者。因此接收者不必相信作者，只需相信自己安裝的核心。

（代管服務做不到這一點，[07 交付模式](07-label-and-distribution.md)有誠實說明與替代方案。）

### 原則六：人只看標籤，而且只看差異
人不會讀程式碼，也不該被要求讀 YAML。人的介面只有：
- 一張**權限標籤**（這個工具要什麼、為什麼）；
- **差異**（新版本比舊版本多要了什麼）；
- **例外**（哪些地方超出一般範圍，需要你特別點頭）。

同意的次數要少而有意義，避免「一直按允許」的疲勞。

### 原則七：誠實標示覆蓋率，並且失敗時關閉
每條通道在每個情境下的保護強度都不同，標籤必須明講：

| 等級 | 意義 |
| --- | --- |
| 🟢 強制 | 核心在技術上阻擋越界行為 |
| 🟡 監看 | 核心看得到並記錄，但無法即時阻擋 |
| 🟠 僅聲明 | 只有作者的聲明，核心無法驗證 |
| ⚪ 無覆蓋 | 殼在此情境下碰不到這條通道 |

任何閘門故障、宣告無法解析、簽章不符時，一律**拒絕執行**，不降級放行。

## 4. 殼明確不做的事

講清楚界線，比宣稱萬能更有價值：

- **不保證功能正確。** 應用在允許範圍內做錯事（算錯、顯示錯資料），殼無法得知。
- **不取代應用層的授權邏輯。** 多人使用的服務中「誰能看誰的資料」仍是應用的責任；殼只能在入口加上身分驗證與流量管制作為外層防護。
- **不防禦主機本身已被入侵的情況。** 殼信任它所在的作業系統與硬體。
- **不對抗願意投入核心漏洞的高階攻擊者。** 隔離強度可以選（程序 → 容器 → 微型虛擬機），但不宣稱絕對。
- **不審查內容是否合法或合乎倫理。**

一句話：**殼限制的是「爆炸半徑」，不是「會不會爆」。**
