# 09 路線圖與待決問題

## 1. 分期

| 指標 | 意義 |
| --- | --- |
| 無人介入安裝成功率 | Agent 安裝這個前提是否成立 |
| 裝殼後功能通過率 | 殼是否過緊到沒人要用 |

## 3. 待決問題

依對設計的影響程度排序。

### 影響大

**Q1　側錄不完整怎麼辦？**
測試涵蓋率低的應用，側錄得到的權限會不足，使用者在強制模式下會頻繁碰壁。選項：(a) 執行期由同意代理臨時核可並回饋成宣告修改提案；(b) 由 Agent 自動探索補足涵蓋；(c) 明確要求最低測試涵蓋才給 L2。三者可能要併用，需要實測決定比重。

**Q2　TLS 檢視的取捨**
機密注入與資料閘門需要看到明文，等於殼對應用做中間人。這帶來相容性問題（憑證綁定）與殼自身成為高價值目標的問題。替代方案是只支援明確的幾家 API 供應商格式而不做通用檢視。需要決定預設值。

**Q3　同意疲勞**
同意太多次，人就會無腦按允許，整個設計就失效了。需要以實際使用資料來調整哪些事該問、哪些事該用預設與保險絲處理。目標是一般工具整個生命週期只需同意一次標籤。

**Q4　代管情境對使用者的保證太弱**
這是最多人實際採用的交付方式，卻是殼最無力的地方。在機密運算普及之前，是否有中間方案（例如由中立方代管殼、作者只提供 Bundle）值得探討。

**Q5　核心的信任如何建立？**
所有保證最終都押在 Warp Core 上。需要獨立的安全審查、可重現建置、盡量小的程式碼量。在這些到位之前，文件與標籤都應註明核心的成熟度。

### 影響中

**Q6　跨平台一致性**
三大作業系統的隔離機制能力不同，同一份宣告在不同平台的覆蓋率會不同。標籤是否要依平台顯示不同的覆蓋率？（傾向：是，由接收者端的核心依實際後端重新計算。）

**Q7　殼內需要用到主機資源的應用**
需要 GPU、需要操作主機上的其他應用程式（自動化工具）、需要存取瀏覽器。這類應用與隔離的概念本質上衝突，可能需要專門的「受控橋接」設計，或直接承認不適用。

**Q8　Fitter 的可攜性**
不同的編碼 Agent 能力與工具介面不同。技能檔寫成純文字步驟加上 `warp` 指令是最大公約數，但品質可能參差。是否需要一個參考用的 Fitter 實作作為基準？

**Q9　風險分數的校準**
權重如何訂、是否會被刻意規避（把一條大權限拆成多條小權限）。初期應視為輔助資訊，不作為自動放行的唯一依據。

### 影響小但要決定

- 宣告檔用 YAML 還是更嚴格的格式。
- 帳本的留存期限與隱私預設。
- 命名：專案名稱、指令名稱、副檔名是否維持 Warp。
- 授權條款與治理方式。

## 4. 最大的風險

不是技術，而是**錯誤的安全感**。使用者看到「已包覆」就把最敏感的資料放進一個權限寬鬆、覆蓋率打折的工具裡。

對策貫穿整份設計：覆蓋率誠實標示、「不可以」清單具體列出、例外獨立顯示、信任等級與風險等級分開、文件開頭就寫明殼不保證正確性。這些在實作與宣傳時都不能為了好看而省略。

## 5. 第 1 期已知弱點與未驗證處

誠實列出，避免錯誤的安全感：

- **沒有 seccomp 系統呼叫過濾**：殼內程序沒有任何 capability、無法建立巢狀使用者命名空間，但仍可使用大部分系統呼叫；核心本身的漏洞不在殼的防護範圍內。
- **`spawn` 未強制**：殼內可以執行任何在 `/usr` 等唯讀系統目錄中的程式（仍受同樣的檔案、網路限制）。
- **系統目錄可讀**：`/usr`、`/bin`、`/lib*` 與 `/etc` 的白名單檔案在殼內可讀；`/proc/self/mountinfo` 會透露掛載來源的主機路徑名稱。
- **允許的主機本身可被濫用**：資料可以送往任何已宣告的主機；以子網域萬用字元宣告時，可透過子網域名稱向該網域的 DNS 夾帶資料。
  未中止 TLS 的通道只檢查 SNI，無法檢查加密後的 HTTP Host 標頭。
- **機密遮蔽只比對原文**：若綁定主機以變形（例如 base64）回傳金鑰，殼內可能取得真值；綁定主機若提供轉送或 webhook 功能，也可能被用來轉送金鑰。
- **側錄的檔案證據**以 inotify 取得，看不到「嘗試開啟不存在的路徑」。
- **證據擋不住同一個使用者**：Agent 與核心同一個作業系統使用者時，Agent 讀得到簽章金鑰，可以寫出通過檢查器的側錄檔；
  也可以用 `warp record -- <任意指令>` 錄出真的證據。第 1 期的對策是讓它看得到、可重做（`triggered_by` 綁定實際指令、證據綁定內容雜湊、
  標籤列出依據指令、`warp evidence replay`），而不是宣稱不可偽造。重放只重做證據裡的指令：需要手動操作網頁介面才觸發的行為不會重現，
  應用本身不穩定時也可能偶爾重現不了。詳見 [05](05-agent-fitting-protocol.md) 第 4.1 節。
- **報告與信任等級是本機檔案**：`.warp/reports/` 的探針與強制報告沒有簽章，同一個使用者可直接改寫而讓標籤顯示 L2。要確認請自己執行 `warp probe`；
  接收者一律在自己的機器上重新探測。
- **跨機器交付**：側錄檔以本機金鑰（HMAC）簽章，接收者的核心無法驗證作者機器上的簽章；可以用 `warp evidence replay` 在自己的機器上重做，
  或重新側錄。第 2 期封籤改用公開金鑰簽章後，簽章才能跨機器驗證（仍不改變「證據只表示指令做出了行為」這一點）。
- **帳本**能偵測竄改、刪除、重排，以及（藉由尾端錨點）從尾端截斷；尾端與錨點不符時核心拒絕續寫。但雜湊鏈沒有秘密：
  同一個使用者可以把帳本與錨點整個重寫，本機無法發現。`warp ledger verify` 印出的尾端值抄到別處保存，之後用 `--expect` 比對，才能發現這種重寫。
- **資源上限**是盡力而為：沒有 cgroup 時以 rlimit 代替——記憶體上限（`RLIMIT_DATA`）只限單一程序，殼的總量未受限；
  以 root 執行且沒有 pids cgroup 時，程序數上限無法強制；磁碟只限單一檔案大小與 `/tmp` 容量；CPU 上限未實作。
  每次強制與探測都會把實際的套用方式寫入報告，標籤據此顯示並以 ⚠ 標示未涵蓋整個殼的上限。
- **一般使用者通常沒有 cgroup**：在 cgroup v1 或未委派子樹的 cgroup v2 上，一般使用者無法建立 cgroup，記憶體上限因此退為每個程序個別限制。
  經 systemd 等委派的 cgroup v2 子樹在程式上會嘗試使用，但**尚未實測**（測試環境的控制器都掛在 v1）。
- **一般使用者的附加群組**：非 root 無法在建立使用者命名空間前或後放棄附加群組（`setgroups` 被停用），殼內程序仍帶著執行者的附加群組；
  由於殼內只看得到宣告的路徑與唯讀系統目錄，影響限於這些檔案的群組權限。root 執行時則帶 root 的群組。
- **以 root 執行**時殼內 UID 0 對應主機的 root（無任何 capability，且掛載都是唯讀或宣告過的路徑）；建議以一般使用者執行 warp。
- **實測環境**：Linux 6.18（容器內）、cgroup v1，warp 分別以 root 與一般使用者（uid 47613，無 cgroup 權限）執行，
  正常範例全流程與惡意範例 27 項攻擊、探針 78/78 在兩種身分下都通過；另有對照測試證明同一批測試檔案在沒有殼時確實可被該使用者讀寫刪除。
  cgroup v2（含委派）、其他發行版、較舊核心（< 5.14 時 `RLIMIT_NPROC` 以主機上該使用者的全部程序計數）尚未實測。
- 對內閘門只代理 HTTP；閘門不支援上游（公司）代理；HTTP/2 只以 HTTP/1.1 與應用溝通。

## 6. 實地試驗後的下一步

[11 實地試驗](11-field-trial.md)顯示殼本身守得住，但「Agent 無人介入裝殼」與「交給別人用」還不成立。以下項目應排在第 2 期原訂內容之前或與之並行：

- [ ] 同意流程（`warp approve`），並重新檢視「選定資料夾可寫」是否該是例外（D1）
- [ ] 相依環境的交付：工具鏈聲明、接收者端在殼內安裝相依、雜湊只涵蓋原始碼與鎖定檔（D2）
- [ ] 對外連線命中模型 API 主機卻沒有 `ai` 區段時報錯，並在標籤標示花費未受限（D4）
- [ ] 側錄與測試時的應用目錄可寫覆蓋層、宣告的 `env` 欄位、讓檔案寫入被擋看得見（D7）
- [ ] 網址路徑與查詢字串中的機密注入（D5）
- [ ] 側錄時由閘門注入真金鑰（D3）
- [ ] 宣告中指定測試指令，L2 綁定到該指令的執行結果（D8）
- [ ] 「任意公開網站」對外類別（D6）
- [ ] 改寫原則三：測試證明「加殼後功能沒壞」，權限證據來自 Agent 實際操作
- [ ] 修正 `warp diff` 不報告啟動指令變更、探針對照組用語、標籤不顯示 `denied_by_design`
- [ ] 以上完成後重做同樣的試驗；另需以真人檢驗標籤是否看得懂
