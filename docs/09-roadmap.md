# 09 路線圖與待決問題

## 1. 分期

原則：**先把一種情境做到真的能擋，再擴展情境**。一個漏水的全功能殼比沒有殼更糟，因為它製造錯誤的安全感。

### 第 0 期　規格定案（文件）
- [x] 問題、原則、威脅模型、架構草案（本儲存庫現況）
- [ ] `warp.yaml` 的正式結構描述與檢查規則清單
- [ ] 探針清單與通過標準
- [ ] 標籤的人讀與機讀格式
- [ ] 找 3–5 個真實的 AI 產生應用做紙上演練，檢驗宣告格式是否表達得了

### 第 1 期　最小可用的殼（MVP）
**範圍**：Linux 與 macOS 上的情境 A（命令列）與情境 C（本機網頁），模式一（本機交付）。

| 元件 | MVP 內容 |
| --- | --- |
| 啟動器 | `process` 與 `container` 兩種後端 |
| 檔案閘門 | 合成檔案系統、`APP_DATA`、`USER_PICK` |
| 對外閘門 | 主機白名單、DNS 代答、封鎖區域網路與中繼資料位址 |
| 對內閘門 | 僅本機迴路 + 權杖 |
| 機密代理 | 標頭注入、佔位值 |
| 檢查器 | 全部硬性規則、證據檢核 |
| 模式 | `record`、`enforce`、`probe`（核心探針） |
| 標籤 | 終端機顯示 + JSON |
| Fitter | 一份技能檔，在至少兩種編碼 Agent 上驗證可用 |

**不含**：AI 閘門的工具政策、資料閘門、封籤簽章、Windows、桌面 GUI。

**完成標準**：
- 對 10 個未經挑選的 AI 產生應用，Fitter 能在無人介入（除了三個前置問題與標籤確認）的情況下完成安裝的比例 ≥ 70%。
- 裝殼後原有功能測試通過率 100%（不通過即視為安裝失敗）。
- 確定性探針 100% 被擋。
- 刻意植入的 5 種惡意行為（讀憑證、外傳檔案、偷金鑰、掃內網、刪除殼外檔案）全數被擋。

### 第 2 期　AI 與外掛
- AI 閘門：花費上限、模型白名單、工具風險分級與同意。
- 情境 E：MCP 協定代理、工具描述鎖定。
- 情境 F：自主 Agent 範本、保險絲。
- 封籤與 Bundle 格式、簽章、版本差異。
- 覆寫層模式與試駕模式。

### 第 3 期　代管與組織
- 情境 D：反向代理部署、翻譯為容器平台的原生政策。
- 多使用者的驗證與配額。
- 組織政策檔與自動判讀。
- 情境 G、H。
- Red Team Agent 的參考實作。

### 第 4 期　廣度與生態
- Windows、桌面 GUI（情境 B）。
- `microvm` 與 `wasm` 後端。
- 情境 I 的標籤翻譯。
- 第三方見證（L3）、撤銷機制、公開的標籤查詢。
- 可遠端證明的代管部署。

## 2. 成功指標

| 指標 | 意義 |
| --- | --- |
| 無人介入安裝成功率 | Agent 安裝這個前提是否成立 |
| 裝殼後功能通過率 | 殼是否過緊到沒人要用 |
| 探針與植入攻擊的阻擋率 | 殼是否真的有效 |
| 平均授權條數與例外數 | 最小權限是否真的小 |
| 從拿到 Bundle 到開始使用的時間 | 接收者的摩擦 |
| 每次使用的同意次數 | 是否造成同意疲勞 |
| 執行期額外負擔（啟動時間、延遲） | 是否可接受 |

## 3. 待決問題

依對設計的影響程度排序。

### 影響大

**Q1　側錄不完整怎麼辦？**
測試涵蓋率低的應用，側錄得到的權限會不足，使用者在強制模式下會頻繁碰壁。選項：(a) 執行期由同意代理臨時核可並回饋成宣告修改提案；(b) 由 Agent 自動探索補足涵蓋；(c) 明確要求最低測試涵蓋才給 L2。三者可能要併用，需要實測決定比重。

**Q2　TLS 檢視的取捨**
機密注入與資料閘門需要看到明文，等於殼對應用做中間人。這帶來相容性問題（憑證綁定）與殼自身成為高價值目標的問題。替代方案是只支援明確的幾家 API 供應商格式而不做通用檢視。需要決定預設值。

**Q3　同意疲勞**
同意太多次，人就會無腦按允許，整個設計就失效了。需要以實際使用資料來調整哪些事該問、哪些事該用預設與保險絲處理。目標是一般工具整個生命週期只需同意一次標籤。

**Q4　代管情境對使用者的保證太弱**
這是最多人實際採用的交付方式，卻是殼最無力的地方。在機密運算普及之前，是否有中間方案（例如由中立方代管殼、作者只提供 Bundle）值得探討。

**Q5　核心的信任如何建立？**
所有保證最終都押在 Warp Core 上。需要獨立的安全審查、可重現建置、盡量小的程式碼量。在這些到位之前，文件與標籤都應註明核心的成熟度。

### 影響中

**Q6　跨平台一致性**
三大作業系統的隔離機制能力不同，同一份宣告在不同平台的覆蓋率會不同。標籤是否要依平台顯示不同的覆蓋率？（傾向：是，由接收者端的核心依實際後端重新計算。）

**Q7　殼內需要用到主機資源的應用**
需要 GPU、需要操作主機上的其他應用程式（自動化工具）、需要存取瀏覽器。這類應用與隔離的概念本質上衝突，可能需要專門的「受控橋接」設計，或直接承認不適用。

**Q8　Fitter 的可攜性**
不同的編碼 Agent 能力與工具介面不同。技能檔寫成純文字步驟加上 `warp` 指令是最大公約數，但品質可能參差。是否需要一個參考用的 Fitter 實作作為基準？

**Q9　風險分數的校準**
權重如何訂、是否會被刻意規避（把一條大權限拆成多條小權限）。初期應視為輔助資訊，不作為自動放行的唯一依據。

### 影響小但要決定

- 宣告檔用 YAML 還是更嚴格的格式。
- 帳本的留存期限與隱私預設。
- 命名：專案名稱、指令名稱、副檔名是否維持 Warp。
- 授權條款與治理方式。

## 4. 最大的風險

不是技術，而是**錯誤的安全感**。使用者看到「已包覆」就把最敏感的資料放進一個權限寬鬆、覆蓋率打折的工具裡。

對策貫穿整份設計：覆蓋率誠實標示、「不可以」清單具體列出、例外獨立顯示、信任等級與風險等級分開、文件開頭就寫明殼不保證正確性。這些在實作與宣傳時都不能為了好看而省略。
