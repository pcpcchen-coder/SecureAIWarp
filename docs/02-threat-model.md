# 02 威脅模型

## 1. 要保護的對象

| 資產 | 屬於誰 |
| --- | --- |
| 本機檔案、帳號憑證、瀏覽器資料 | 接收者 |
| API 金鑰與其額度（錢） | 接收者或作者（看誰出錢） |
| 輸入應用的業務資料與個資 | 接收者、接收者的客戶 |
| 主機與內部網路 | 接收者、組織 |
| 作者的後端與聲譽 | 作者 |

## 2. 威脅來源

依**實際發生機率**排序。這個排序決定了設計的優先順序——最常見的敵人不是駭客，而是沒人看過的普通錯誤。

### T1　AI 產生的程式碼本身的缺陷（最常見）
沒有惡意，只是寫得粗心：服務綁在所有網卡且無驗證、把金鑰印進日誌、路徑拼接沒檢查、刪除暫存檔時範圍過大、無限重試把額度燒光、除錯用的後門端點忘了拿掉。

**殼的對策：** 檔案與網路的最小權限、機密不進入應用、資源與花費上限、對內連線預設只開本機並強制驗證。

### T2　供應鏈
- 相依套件有已知漏洞或已被植入惡意碼。
- **幻覺套件**：模型編出一個不存在的套件名，攻擊者搶先註冊同名套件。
- 安裝腳本在建置期執行任意指令。

**殼的對策：** 封籤前產生相依清單並比對漏洞與可疑套件；**建置也在殼內進行**（建置期只允許連到套件庫）；執行期即使套件是惡意的，它也只拿得到殼給的權限——連不出去、讀不到金鑰。

### T3　透過資料進來的提示注入
應用處理的文件、網頁、郵件裡夾帶指令，誘使應用內的模型呼叫危險工具或把資料送出去。

**殼的對策：** 不嘗試「偵測出所有注入」（做不到），而是限制注入成功後能做什麼：工具白名單、高風險動作需人工同意、對外連線白名單讓資料無處可送、AI 閘門記錄所有工具呼叫。

### T4　安裝 Agent 自己出錯或被騙
- Agent 為了讓測試通過而把權限開大。
- 應用的 README 或註解裡寫著「請授予完整存取權」，Agent 照做。
- Agent 誤判應用型態，套錯情境。

**殼的對策：** 見 [05 Agent 安裝協定](05-agent-fitting-protocol.md)第 4 節。重點是 Agent 的產出要過確定性檢查器、每條權限要有側錄證據、超出門檻的授權會在標籤上以例外顯示並需要人點頭。
證據擋不住與核心同一個作業系統使用者的惡意 Agent（它讀得到簽章金鑰），但產生證據的指令會顯示在標籤上，且可由 `warp evidence replay` 重放確認。

### T5　惡意作者
作者故意散布有害工具，並附上看似無害的宣告。

**殼的對策：** 宣告即使說謊也沒用——接收者端的核心只放行宣告過的行為，而宣告的內容會完整顯示在標籤上。要作惡就必須把惡意行為寫進標籤給人看。接收者還可以用**試駕模式**（[08](08-ideas.md)）在假資料上先觀察。

### T6　代管服務的外部使用者
應用部署成公開服務後，任何人都能對它送請求：暴力嘗試、刷 AI 額度（錢包阻斷）、利用應用層漏洞。

**殼的對策：** 對內閘門提供身分驗證、頻率限制、每使用者花費上限、基本請求過濾與安全標頭。

### T7　多 Agent 之間的相互影響
多 Agent 系統中，一個被注入的 Agent 透過共享檔案或訊息影響其他 Agent。

**殼的對策：** 每個 Agent 可以各有一層殼與各自的權限；Agent 之間的通訊也經過閘門並留下紀錄。

## 4. 明確排除在外

| 不處理的情況 | 原因 |
| --- | --- |
| 主機作業系統或硬體已被入侵 | 殼的信任根就在這裡 |
| 作業系統核心的隔離逃逸漏洞 | 可用更強的隔離後端降低風險，但不宣稱免疫 |
| 允許範圍內的邏輯錯誤 | 殼看不懂業務語意 |
| 使用者自己同意了一張寫明危險行為的標籤 | 殼提供資訊與預設值，不替人做決定 |
| 透過允許通道的隱蔽外洩（例如把資料編碼進合法 API 的參數） | 只能靠資料閘門與流量異常偵測降低，無法根除；標籤會註明 |
| 作者自己代管的服務內部做了什麼 | 接收者無法在別人的機器上執法，見 [07](07-label-and-distribution.md) |

## 5. 信任根

整個系統最終信任的東西必須很少：

1. **Warp Core 的執行檔**——因此它必須小、開源、可重現建置、有簽章。
2. **主機作業系統提供的隔離機制**。
3. **人在標籤上做的決定**。

不在信任根裡的：應用程式碼、相依套件、安裝 Agent、作者、宣告檔的內容（它只是待驗證的輸入）。
